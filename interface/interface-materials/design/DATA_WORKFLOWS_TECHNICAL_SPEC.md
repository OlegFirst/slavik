- Images (JPG/PNG): Схемы, диаграммы

#### **ИСТОЧНИК #3: ИНТЕГРАЦИИ С СИСТЕМАМИ (ADVANCED)**

**Что это:**
Прямое подключение к HR, ERP, IT monitoring системам организации.

**Зачем:**
- Автоматический сбор данных (нет ручного ввода)
- Real-time обновления (сотрудник уволился → BCP обновлён автоматически)

**Какие интеграции:**

**1. HR-системы (BambooHR, Workday, SAP SuccessFactors):**
   - Получаем: Список сотрудников, роли, контакты
   - Используем: Автозаполнение кризисной команды, обновление BCP

**2. ERP-системы (SAP, Odoo, Microsoft Dynamics):**
   - Получаем: Бизнес-процессы, финансовые данные, зависимости
   - Используем: BIA (financial impact), приоритизация процессов

**3. IT Monitoring (Prometheus, Datadog, Zabbix):**
   - Получаем: Инциденты (downtime, outages)
   - Используем: Автоматическая активация BCP, метрики MTTR

**4. Calendar Systems (Google Calendar, Outlook):**
   - Получаем: Расписание сотрудников
   - Используем: Планирование exercises, доступность кризисной команды

**Пример: Интеграция с HR-системой**

```
🔗 HR INTEGRATION (BambooHR API)

ЗАПРОС AI:
GET /employees?status=active

ОТВЕТ:
[

    "department": "Surgery",
    "phone": "+380-67-XXX-XXXX",
    "email": "smirnov@hospital.ua",
    "start_date": "2018-03-15"
  },
  ... (450 сотрудников)
]

AI ОБРАБОТКА:
1. Извлекаем критичных сотрудников (heads of departments)
2. Автозаполняем кризисную команду:
   - Medical Lead: Смирнов Пётр (Head of Surgery)
   - ICU Lead: Кузнецова Анна (Head of ICU)
   - ...

3. Подписываемся на webhook (увольнение):

     "event": "employee.terminated",

   }

4. Когда Смирнов увольняется:
   → Webhook срабатывает

   → Уведомляет BCM менеджера: "Смирнов уволился, обновите кризисную команду"
```

### 1.2 DATA QUALITY & VALIDATION

**Проблема:**
Пользователи вводят неполные/некорректные данные.

**Решение: AI VALIDATION ENGINE**

**Валидация #1: Completeness Check**

```
AI ПРОВЕРЯЕТ:
- Все обязательные поля заполнены?
- Критичные процессы имеют RTO/RPO?
- Зависимости определены?

ПРИМЕР:
Процесс: "Экстренная хирургия"
- RTO: ✅ 0 часов
- RPO: ❌ НЕ ЗАПОЛНЕНО
- Зависимости: ✅ 3 (Электричество, Кислород, IT)

AI → WARNING:
"RTO для 'Экстренная хирургия' не указан.
 Рекомендуется указать, чтобы BIA был полным."
```

**Валидация #2: Consistency Check**

```
AI ПРОВЕРЯЕТ ЛОГИКУ:

ПРИМЕР НЕСООТВЕТСТВИЯ:
- Процесс: "Экстренная хирургия"
- Критичность: HIGH
- RTO: 48 часов ❌

AI → ERROR:
"Несоответствие: Процесс критичный (HIGH), но RTO = 48 часов (слишком долго).
 Обычно для HIGH критичности RTO < 4 часов.
 Проверьте, правильно ли указан RTO."

РЕКОМЕНДАЦИЯ AI:
На основе 347 похожих организаций:
- "Экстренная хирургия" в больницах: RTO среднее = 0-2 часа
```

**Валидация #3: Benchmarking**

```
AI СРАВНИВАЕТ С INDUSTRY STANDARDS:

 Добавить их?"

```

KNOWLEDGE GRAPH: БОЛЬНИЦА "ЗДОРОВЬЕ"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

NODES (узлы):

[ПРОЦЕССЫ]
- Экстренная хирургия (CRITICAL, RTO: 0h)
- Приёмное отделение (HIGH, RTO: 2h)
- Реанимация ICU (CRITICAL, RTO: 0h)
- Лабораторная диагностика (MEDIUM, RTO: 4h)

[ЛЮДИ]
- Иванова Елена (Директор, Crisis Manager)
- Смирнов Пётр (Head of Surgery, Medical Lead)
- Кузнецова Анна (Head of ICU)
- Васильев Игорь (IT Director)

[РИСКИ]
- Ransomware атака (вероятность: 40%, impact: €150K)
- Отключение электричества (вероятность: 20%, impact: €45K)
- Пожар (вероятность: 5%, impact: €500K)

EDGES (связи):

[ЗАВИСИМОСТИ]
"Экстренная хирургия" --depends_on--> "Электричество"
"Экстренная хирургия" --depends_on--> "Кислород"

"IT-системы EMR" --depends_on--> "Электричество"

"IT-системы EMR" --owned_by--> "Васильев Игорь"

[RISK_IMPACTS]
"Ransomware атака" --impacts--> "IT-системы EMR"
"Отключение электричества" --impacts--> "Электричество"
"Пожар" --impacts--> "Экстренная хирургия"

АНАЛИЗ ГРАФА (AI):

КРИТИЧНЫЕ УЗЛЫ (single point of failure):
1. Электричество: 5 процессов зависят напрямую
   → ВЫСОКИЙ РИСК!
   → Рекомендация: Генераторы, UPS, backup plan

2. IT-системы EMR: 3 критичных процесса зависят
   → ВЫСОКИЙ РИСК!
   → Рекомендация: Backup системы, paper-based fallback

CASCADING FAILURES (каскадные сбои):
Если "Электричество" падает:
→ "Кислород" падает (зависит от электричества)
→ "IT-системы EMR" падают (зависит от электричества)
