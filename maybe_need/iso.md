        ↓

ДЕНЬ 2: Больница работает нормально

📋 ЧТО ТАКОЕ ISO 22301?
Официальное Определение:
ISO 22301 - Международный стандарт для 
Business Continuity Management System (BCMS)
= Система Управления Непрерывностью Бизнеса
Нормальное Определение:
ISO 22301 = Чеклист из 200+ требований, 
который гарантирует что твоя компания:

1. ЗНАЕТ что может пойти не так
2. ПОДГОТОВИЛАСЬ к этим проблемам
3. МОЖЕТ быстро восстановиться
4. УЧИТСЯ от каждого инцидента
📖 СТРУКТУРА СТАНДАРТА (10 Clauses)
Clause 4: Context of the Organization (Контекст Организации)
Суть: Пойми свой бизнес
Вопросы:
- Кто твои stakeholders? (клиенты, регуляторы, партнеры)
- Что для них важно?
- Какие внешние риски? (конкуренты, законы, стихийные бедствия)
- Какие внутренние риски? (технологии, люди, процессы)

Пример:
Больница определяет:
✅ Stakeholders: Пациенты, врачи, регуляторы (Минздрав)
✅ Критично: Непрерывность медицинских услуг
✅ Внешние риски: Пандемия, землетрясение, кибератаки
✅ Внутренние риски: Устаревшее оборудование, нехватка персонала
Clause 5: Leadership (Руководство)
Суть: CEO должен быть вовлечен
Требования:
- Топ-менеджмент ОБЯЗАН поддерживать BCM (не делегировать)
- Назначить BCM Manager с полномочиями
- Выделить бюджет и ресурсы
- BCM Policy подписана CEO

Почему важно:
❌ Без поддержки CEO: BCM становится формальностью (галочка)
✅ С поддержкой CEO: BCM встроен в культуру компании

Пример:
CEO больницы:
✅ Подписывает BCM Policy
✅ Выделяет €500K бюджет на BC Plans
✅ Ежеквартально участвует в BC Committee
✅ Лично тестирует emergency evacuation plan
Clause 6: Planning (Планирование)
Суть: Определи ЧТО защищать
Требования:
- Risk Assessment (оценка рисков)
- Business Impact Analysis (BIA)
- Определить Recovery Time Objective (RTO)
- Определить Recovery Point Objective (RPO)

КЛЮЧЕВОЙ ИНСТРУМЕНТ: BIA (Business Impact Analysis)

Что такое BIA?
= Анализ какие процессы КРИТИЧНЫ для выживания компании

Пример BIA для больницы:

┌────────────────────────────────────────────────────────┐
│ Процесс             │ RTO    │ Макс.Downtime │ Воздействие│
├────────────────────────────────────────────────────────┤
│ Экстренная помощь   │ 0 мин  │ 0 часов       │ КРИТИЧНО   │
│ Электронные карты   │ 30 мин │ 4 часа        │ ВЫСОКОЕ    │
│ Назначение лекарств │ 1 час  │ 8 часов       │ ВЫСОКОЕ    │
│ Запись на прием     │ 24 часа│ 3 дня         │ СРЕДНЕЕ    │
│ Бухгалтерия         │ 72 часа│ 1 неделя      │ НИЗКОЕ     │
└────────────────────────────────────────────────────────┘

RTO (Recovery Time Objective):
= Максимальное время простоя которое можно допустить

Если RTO = 30 минут для электронных карт:
→ Значит через 30 минут после сбоя система ДОЛЖНА работать
→ Иначе = серьезные последствия (пациенты в опасности)
Clause 7: Support (Поддержка)
Суть: Нужны ресурсы, люди, документация
Требования:
- Компетентные люди (обученные)
- Документация (BCP, процедуры)
- Коммуникация (как связываться во время кризиса)
- Информация (какие данные критичны)

Пример:
Больница обеспечивает:
✅ 5 человек обучены Crisis Management (80 часов тренинга)
✅ BCP документ (120 страниц, обновляется каждые 6 месяцев)
✅ Emergency call tree (кого звонить при пожаре, кибератаке, etc.)
✅ Backup медкарт пациентов (ежедневный бэкап, хранится 30 дней)
Clause 8: Operation (Операции) ⭐ САМЫЙ ВАЖНЫЙ
Суть: Создай планы восстановления
Требования:
- Business Continuity Plans (BCP) для каждого критичного процесса
- Incident Response Procedures
- Crisis Management Team
- Emergency Contact Lists
- Backup Resources (люди, оборудование, помещения)

Что такое BCP (Business Continuity Plan)?

= Пошаговая инструкция "Что делать если X сломалось"

Пример BCP для "Сбой электронных медкарт":

│ BCP: Сбой Электронной Системы Медкарт                │
├──────────────────────────────────────────────────────┤
│ АКТИВАЦИЯ (Когда запускать этот план):              │
│ • Система недоступна >15 минут                       │
│ • Влияет >10% отделений больницы                     │
│                                                      │
│ ФАЗА 1: НЕМЕДЛЕННЫЙ ОТВЕТ (0-30 минут)              │
│ ☐ 1. Уведомить Crisis Manager (Звонок: +X)          │
│ ☐ 2. Активировать Crisis Team (SMS всем)            │
│ ☐ 3. Переключиться на бумажные карты                │

│      Ответственный: Медсестра главная               │
│ ☐ 4. Уведомить отделения (Email шаблон #7)          │
│                                                      │
│ ФАЗА 2: ВОССТАНОВЛЕНИЕ (30 мин - 4 часа)            │
│ ☐ 5. IT Team диагностирует проблему                 │
│      Если hardware → заменить сервер (склад B)      │
│      Если software → откатить на backup              │
│ ☐ 6. Восстановить из backup (Last: 2 AM сегодня)    │

│ • Бумажные формы: Склад А                            │
│ • IT Support 24/7: +X (primary), +Y (backup)        │
│                                                      │
│ КОММУНИКАЦИЯ:                                        │
│ • Врачам: "Используйте бумажные карты временно"     │
│ • Пациентам: "Небольшая задержка, извините"         │
│ • Регуляторам: НЕ требуется (если <8 часов)         │
└──────────────────────────────────────────────────────┘

ВОТ ЧТО ТАКОЕ BCP!
= Детальная инструкция на каждый кризис
Требования ISO 22301 к BCP:
✅ BCP должен быть для КАЖДОГО критичного процесса (из BIA)
✅ BCP должен быть ПРОТЕСТИРОВАН (минимум 1 раз в год)
✅ BCP должен быть ДОСТУПЕН offline (что если интернет не работает?)
✅ BCP должен быть ПОНЯТЕН (любой человек может следовать)
✅ BCP должен ОБНОВЛЯТЬСЯ (после каждого инцидента)
Clause 9: Performance Evaluation (Оценка Эффективности)
Суть: Проверяй работает ли твой план
Требования:
- Monitoring (метрики BCM)
- Internal Audit (ежегодная проверка)
- Management Review (CEO проверяет раз в квартал)
- Testing & Exercises (тренировки)

КЛЮЧЕВОЕ: TESTING!

Типы тестов:
1. Tabletop Exercise (настольная игра)
   = Команда сидит за столом, обсуждает сценарий
   Пример: "Представьте пожар в датацентре. Что делаем?"
   
2. Simulation Exercise (симуляция)
   = Притворяемся что кризис реален, но не трогаем prod
   Пример: IT переключается на backup, но клиенты не знают
   
3. Full Exercise (полная тренировка)
   = Реально переключаемся на backup, все как в бою
   Пример: В субботу 3 AM отключаем primary datacenter

ISO 22301 требует:
✅ Минимум 1 exercise в год для каждого критичного процесса
✅ Документировать результаты
✅ Исправлять найденные проблемы
Clause 10: Improvement (Улучшение)
Суть: Учись от каждого инцидента
Требования:
- Корректирующие действия (если нашли проблему → исправь)
- Непрерывное улучшение (каждый год лучше чем предыдущий)

Пример:
После exercise нашли:
❌ Backup server не имел последних патчей
❌ Контакт IT Manager устарел (он уволился 3 месяца назад)
❌ Процедура восстановления заняла 2 часа (RTO = 30 минут)

Корректирующие действия:
✅ Автоматическое патчирование backup сервера
✅ Обновить emergency contact list (новый IT Manager)
✅ Оптимизировать процедуру восстановления → 25 минут

💰 ЗАЧЕМ КОМПАНИИ СЕРТИФИЦИРУЮТСЯ?
4 Основные Причины:
1. Regulatory Requirement (Требование регулятора)
Примеры:
- Банки в ЕС: GDPR + Banking regulations требуют BCM
- Больницы: Healthcare regulations требуют disaster recovery
- Critical infrastructure: Правительство требует резервирование

Если НЕ сертифицирован:
→ Штраф €50K-500K
→ Потеря лицензии
→ Уголовная ответственность (в крайних случаях)
2. Customer Requirement (Требование клиентов)
B2B клиенты спрашивают:
"У вас есть ISO 22301?"

Если НЕТ:
→ Клиент не подпишет контракт
→ Особенно крупные enterprise клиенты

Пример:
Amazon требует от всех поставщиков AWS:
✅ ISO 22301 или эквивалент
✅ Proof of disaster recovery tests
3. Risk Management (Управление рисками)
CEO понимает:
"Один день простоя = €500K убытков"
"ISO 22301 = страховка от простоя"

ROI расчет:
- Стоимость сертификации: €50K (первый год)
- Стоимость одного кризиса: €2M (без плана)
- Стоимость кризиса с планом: €200K
- Экономия: €1.8M

Окупается с первого инцидента!
4. Competitive Advantage (Конкурентное преимущество)
Маркетинг:
"Мы ISO 22301 сертифицированы"
= "Мы надежны, можете нам доверять"

Особенно важно для:
- Финтех (деньги людей)
- Healthcare (жизнь людей)
- Cloud providers (бизнес клиентов зависит от вас)

🎯 ФИНАЛЬНАЯ СУТЬ ISO 22301
Одной Аналогией:
ISO 22301 = Страховка + План Эвакуации + Пожарные Учения

Для твоего дома:
❌ Без плана: Пожар → паника → люди умирают → дом сгорел
✅ С планом: Пожар → эвакуация (2 мин) → все живы → страховая платит

Для твоего бизнеса:
❌ Без ISO 22301: Кризис → паника → бизнес умирает
✅ С ISO 22301: Кризис → plan activated → бизнес выживает
Три Главных Компонента:
1. ЗНАЕШЬ ЧТО КРИТИЧНО (BIA)
   = Какие процессы НЕЛЬЗЯ терять

2. ИМЕЕШЬ ПЛАН (BCP)
   = Что делать когда случится worst case

3. ТРЕНИРУЕШЬСЯ (Exercises)
   = Проверяешь план работает ли

💡 ФУНДАМЕНТАЛЬНАЯ ИДЕЯ
Главный Вопрос, На Который Отвечает Стандарт:
"Как гарантировать что организация ВЫЖИВЕТ 
 при любом кризисе?"
Не просто "выживет", а:
✅ Продолжит обслуживать клиентов
✅ Сохранит репутацию
✅ Минимизирует финансовые потери
✅ Защитит жизни людей (если применимо)
✅ Выполнит обязательства перед stakeholders
🧬 ДНК СТАНДАРТА (3 Фундаментальных Принципа)
Принцип #1: ПРЕДСКАЗУЕМОСТЬ > РЕАКТИВНОСТЬ
Обычный подход (реактивный):
Кризис → Паника → "Что делать?!" → Импровизация → Хаос

Пример:
Пожар в офисе
↓
Люди не знают куда бежать
Директор звонит в пожарную (5 минут чтобы найти номер)
Сервера горят (никто не думал про backup)
Клиентская база потеряна
Бизнес мертв
ISO 22301 подход (проактивный):
ДО кризиса → Анализ → Планирование → Тренировка
↓
Кризис → План активирован → Предсказуемые действия → Контроль

Пример:
Пожар в офисе
↓
8:00 AM - Сработала пожарная сигнализация
8:01 AM - Автоматическая эвакуация (согласно плану)
8:02 AM - Автоматический звонок в пожарную (система)
8:05 AM - Все эвакуированы (по emergency routes)
8:10 AM - Crisis Manager активирует BCP
8:15 AM - IT переключается на cloud backup
8:30 AM - Бизнес работает удаленно
10:00 AM - Клиенты даже не заметили проблему
Ключ: Все действия ПРЕДОПРЕДЕЛЕНЫ до кризиса, НЕ ИМПРОВИЗАЦИЯ во время.
Принцип #2: СИСТЕМНОСТЬ > ГЕРОИЗМ
Проблема традиционного подхода:
Компания зависит от "героя"

Пример:
"У нас есть Петя. Он знает как восстановить сервера.
 Если что-то сломается - зовем Петю."

Что если:
❌ Петя в отпуске на Бали?
❌ Петя заболел?
❌ Петя уволился?
❌ Петя попал под машину?

→ Бизнес МЕРТВ
ISO 22301 подход:
Компания НЕ зависит от конкретных людей

Документировано:
✅ ЧТО делать (процедуры)
✅ КАК делать (шаг за шагом)
✅ КТО делает (роли, не имена)
✅ ЧЕМ делать (ресурсы, инструменты)

Результат:
→ ЛЮБОЙ обученный человек может выполнить
→ Нет single point of failure в людях
→ Знания в СИСТЕМЕ, не в головах
Пример:
НЕ ISO 22301:
"Если сервера упали, звони Пете: +7-XXX"

ISO 22301:
"Если сервера упали:
 Роль: Infrastructure Engineer (текущий: Петя, backup: Вася)
 Процедура: /docs/server_recovery.pdf (20 шагов)
 Инструменты: Ansible playbook (автоматизировано 90%)
 Контакты: Primary: +7-XXX, Backup: +7-YYY
 Эскалация: Если не восстановлено за 30 мин → звони CTO"
Ключ: СИСТЕМА работает, не отдельные герои.
Принцип #3: НЕПРЕРЫВНОЕ УЛУЧШЕНИЕ > СТАТИЧНЫЙ ПЛАН
Проблема статичного плана:
2020: Написали BCP
2021: Положили в шкаф
2022: Забыли про него
2023: Кризис!
2023: Открыли BCP → он УСТАРЕЛ
      - Контакты неправильные (люди уволились)
      - Процедуры не работают (технологии изменились)
      - Backup не работает (никто не тестировал 3 года)
ISO 22301 подход:
ЦИКЛ PDCA (Plan-Do-Check-Act) - БЕСКОНЕЧНЫЙ

Каждый год:
✅ PLAN: Обновить risk assessment (новые риски?)
✅ DO: Обновить BCP (новые процессы? новые люди?)
✅ CHECK: Протестировать (exercise) → найти проблемы
✅ ACT: Исправить проблемы → начать цикл заново

Результат:

🏗️ АРХИТЕКТУРА СТАНДАРТА (HLS - High Level Structure)
Почему Именно 10 Clauses?
ISO использует УНИВЕРСАЛЬНУЮ структуру для ВСЕХ стандартов менеджмента:
Clause 1-3: Введение (Scope, References, Terms)
           ↓
Clause 4-6: СТРАТЕГИЯ (Context, Leadership, Planning)
           ↓
Clause 7-8: ИСПОЛНЕНИЕ (Support, Operation)
           ↓
Clause 9-10: КОНТРОЛЬ (Evaluation, Improvement)
Это называется HLS (High Level Structure) - одинаково для:
ISO 22301 (BCM)
ISO 27001 (Information Security)
ISO 9001 (Quality Management)
ISO 14001 (Environmental Management)
Зачем? → Легко интегрировать несколько стандартов → Если у тебя уже есть ISO 27001, добавить ISO 22301 легче

Концепция #1: BIA (Business Impact Analysis)
Что это РЕАЛЬНО значит?
BIA отвечает на вопрос:
"Если ЭТОТ процесс сломается, как БЫСТРО мы умрем?"

Метафора:
Представь организацию = человек

Критичные процессы = жизненно важные органы:
- Сердце: RTO = 0 минут (остановка = смерть)
- Легкие: RTO = 0 минут (остановка = смерь)
- Печень: RTO = несколько часов (можно компенсировать)
- Желудок: RTO = несколько дней (можно голодать)
- Волосы: RTO = бесконечность (не критично)

BIA для больницы:
- Экстренная помощь = СЕРДЦЕ (RTO = 0 мин)
- Электронные карты = ЛЕГКИЕ (RTO = 30 мин)
- Запись на прием = ЖЕЛУДОК (RTO = 24 часа)
- Веб-сайт = ВОЛОСЫ (RTO = 1 неделя)
Математика BIA:
Для каждого процесса определяем:

1. MTD (Maximum Tolerable Downtime)
   = Максимальное время простоя до КАТАСТРОФИЧЕСКИХ последствий
   
   Пример: Электронные карты
   - 0-30 мин: Неудобно (можно бумагу)
   - 30 мин - 4 часа: Серьезно (операции задерживаются)
   - 4-8 часов: Критично (пациенты в опасности)
   - >8 часов: КАТАСТРОФА (смерти, судебные иски)
   
   MTD = 8 часов

2. RTO (Recovery Time Objective)
   = Целевое время восстановления (с запасом до MTD)
   
   RTO = MTD × 0.2-0.5 (оставляем буфер)
   RTO = 8 часов × 0.25 = 2 часа
   
   Почему буфер? Что если восстановление пойдет не по плану?

3. RPO (Recovery Point Objective)
   = Сколько данных можем потерять?
   
   Пример:
   - Backup каждые 4 часа → RPO = 4 часа
   - Потеряем максимум 4 часа данных
   
   Для критичных систем: RPO = 0 (real-time replication)

4. Financial Impact
   = Финансовое воздействие простоя
   
   Формула:
   Impact/час = (Потерянная выручка) + (Штрафы) + (Репутация)
   
   Пример больницы:
   - Потерянная выручка: €5K/час (отмененные операции)
   - Штрафы регулятора: €10K/час
   - Репутация: €20K/час (долгосрочно)
   TOTAL: €35K/час
   
   За 8 часов (MTD): €280K убытков
Вывод BIA:

🎯 ФИЛОСОФИЯ СТАНДАРТА (Зачем Все Это?)
Главная Философия: RESILIENCE (Устойчивость)
ISO 22301 не про "избежать проблем" ISO 22301 про "выжить несмотря на проблемы"
Метафора: Дерево в шторм

Слабое дерево:
→ Жесткое, не гнется
→ Ветер → дерево ломается
→ Дерево мертво

Сильное дерево (resilient):
→ Гибкое, гнется на ветру
→ Ветер → дерево гнется, но не ломается
→ Шторм прошел → дерево выпрямилось
→ Дерево живо и даже СИЛЬНЕЕ (корни глубже)

Организация с ISO 22301:
→ Гибкая
→ Кризис → организация адаптируется (BCP)
→ Кризис прошел → бизнес восстановлен
→ Организация УЧИТСЯ (улучшает планы)
4 Уровня Resilience:
УРОВЕНЬ 1: FRAGILE (Хрупкий)
Кризис → Бизнес умирает
Пример: Нет плана, нет backup

УРОВЕНЬ 2: ROBUST (Крепкий)
Кризис → Бизнес выдерживает удар (но страдает)
Пример: Есть backup, но долгое восстановление

УРОВЕНЬ 3: RESILIENT (Устойчивый) ← ISO 22301 ЦЕЛь
Кризис → Бизнес быстро восстанавливается
Пример: BCP активирован, RTO соблюдено

УРОВЕНЬ 4: ANTIFRAGILE (Анти-хрупкий)
Кризис → Бизнес становится СИЛЬНЕЕ
Пример: Учимся от кризиса, конкуренты умерли - мы выросли
ISO 22301 цель = RESILIENT (уровень 3) Наша AI платформа цель = ANTIFRAGILE (уровень 4) Как?
AI учится от каждого кризиса
Каждый пользователь делает систему умнее
Следующий кризис → еще лучше подготовлены

- Стоимость кризиса БЕЗ плана: €2M
- Стоимость кризиса С планом: €200K
- Экономия: €1.8M

Expected Value расчет:
EV без плана = 0.15 × €2M = €300K убытков/год
EV с планом = €50K (cert) + 0.15 × €200K = €80K/год

Экономия: €220K/год

ROI = 440% в первый год!
2. "Мы слишком заняты"
Мышление: "Нет времени писать планы.
           Нужно делать настоящую работу."

Реальность:
Время на сертификацию:
- Без AI: 500-800 часов work
- С нашей платформой: 50-80 часов (AI делает 95%)

Время на кризис БЕЗ плана:
- Недели хаоса
- Месяцы восстановления
- Годы восстановления репутации

Время на кризис С планом:
- Часы контролируемого восстановления
- Дни возврата к нормальной работе
- Репутация даже выросла

"Слишком занят" = ложная экономия
3. "Это бюрократия, формальность"
Мышление: "Просто галочка для регулятора.
           На практике не работает."

Реальность (если делать правильно):
- BCP НЕ должен быть 200-страничным PDF
- BCP должен быть ПРАКТИЧНЫМ:
  → 1-страничная checklist для каждого сценария
  → Доступна offline (что если интернет не работает?)
  → Тестируется регулярно (знаем что работает)
  
Если BCP = толстая книга на полке → ЭТО НЕПРАВИЛЬНО
Если BCP = простые checklist которые все знают → ПРАВИЛЬНО

Наша платформа:
→ Генерирует ПРАКТИЧНЫЕ planы (не бюрократию)
→ Интерактивные checklists (не PDF)

📋 Раздел 6: Планирование ⭐ КРИТИЧНО
Суть: Определи ЧТО защищать и КАК
6.1: BIA (Business Impact Analysis)
Что это? Анализ какие процессы КРИТИЧНЫ для выживания Метафора:
Организация = Человек

Критичные процессы = Жизненно важные органы:
- Сердце: остановка = немедленная смерть
- Легкие: остановка = смерть через минуты
- Печень: повреждение = смерть через часы/дни
- Желудок: без еды = смерть через недели
- Волосы: потеря = НЕ критично

BIA определяет:
Что = "сердце" (RTO = минуты)?
Что = "печень" (RTO = часы)?
Что = "волосы" (RTO = можно не восстанавливать)?
Пример BIA для НПО (гуманитарная помощь):
┌────────────────────────────────────────────────────────────┐
│ Процесс              │ RTO    │ Макс.Простой │ Критичность │
├────────────────────────────────────────────────────────────┤
│ Доставка гум.помощи  │ 4 часа │ 24 часа      │ КРИТИЧНО    │
│ Связь с волонтерами  │ 2 часа │ 8 часов      │ ВЫСОКАЯ     │
│ База данных бенефиц. │ 8 часов│ 3 дня        │ ВЫСОКАЯ     │
│ Прием пожертвований  │ 24 часа│ 1 неделя     │ СРЕДНЯЯ     │
│ Веб-сайт             │ 3 дня  │ 2 недели     │ НИЗКАЯ      │
│ Внутренний email     │ 1 день │ 1 неделя     │ НИЗКАЯ      │
└────────────────────────────────────────────────────────────┘

RTO (Recovery Time Objective):
= Максимальное время простоя которое можно допустить

Если доставка помощи остановлена >24 часов:
→ Люди в зоне бедствия без еды/воды
→ Репутационный ущерб (СМИ)
→ Потеря доверия доноров
→ Возможны человеческие жертвы

Поэтому RTO = 4 часа (большой запас безопасности)
RPO (Recovery Point Objective):
= Сколько данных можем потерять?

Пример:
База данных бенефициаров (кто получил помощь)

Backup каждые 24 часа → RPO = 24 часа
Потеряем максимум 1 день записей

Для критичных данных: RPO = 0
→ Real-time репликация в резервную БД
Финансовое воздействие:
Формула:
Убыток/час = Потерянная работа + Репутация + Регуляторные штрафы

Пример (НПО):
Доставка помощи остановлена:
- Потерянная эффективность: €2K/час (простаивают волонтеры)
- Репутация: €5K/час (доноры уходят)
- Регуляторные: €3K/час (нарушение обязательств)
ИТОГО: €10K/час

За 24 часа (макс.простой): €240K убытков

Вывод: Стоит инвестировать в резервирование!
6.2: Risk Assessment (Оценка Рисков)
Для каждого риска определяем:
1. Вероятность (Likelihood)
   Как часто может случиться?
   
   1 = Редко (раз в 100 лет)
   2 = Маловероятно (раз в 10 лет)
   3 = Возможно (раз в год)
   4 = Вероятно (несколько раз в год)
   5 = Почти точно (постоянно)

2. Воздействие (Impact)
   Насколько серьезно если случится?
   
   1 = Незначительное
   2 = Малое
   3 = Умеренное
   4 = Серьезное
   5 = Катастрофическое

3. Риск = Вероятность × Воздействие

Приоритет = Риск
Пример матрицы рисков (НПО):
┌──────────────────────────────────────────────────────────┐
│ Риск              │ Вероятн.│ Воздейст.│ Риск │ Приоритет│
├──────────────────────────────────────────────────────────┤
│ Кибератака        │    4    │    5     │  20  │    #1    │
│ Потеря финансир.  │    3    │    5     │  15  │    #2    │

│ Сбой электричества│    4    │    2     │   8  │    #6    │
└──────────────────────────────────────────────────────────┘

8.1: Что Такое BCP?
BCP (Business Continuity Plan) =
Пошаговая инструкция "Что делать если X сломалось"

НЕ теория, а ПРАКТИКА:
❌ НЕ 200-страничный документ который никто не читает

📊 Раздел 9: Оценка Эффективности
Суть: Проверяй работает ли план (ОБЯЗАТЕЛЬНО!)
9.1: Тестирование (Exercises)
3 типа учений: 1. Tabletop Exercise (Настольная игра)
Что: Команда сидит за столом, обсуждает сценарий
Время: 2-3 часа
Частота: 2 раза в год

Пример:
Facilitator: "Представьте: пожар в офисе в 3 AM.
              Что вы делаете?"

Crisis Manager: "Я звоню в пожарную, потом..."
Tech Lead: "Подожди, я сначала проверю backup..."
Facilitator: "Backup сервер тоже сгорел."
Tech Lead: "О нет! Тогда... cloud backup?"
Facilitator: "Сколько времени на восстановление?"
Tech Lead: "Хм... я не знаю точно..."

→ НАЙДЕНА ПРОБЛЕМА: Нужна четкая процедура!

Результат:
✅ Дешево (бесплатно)
✅ Находит логические проблемы
✅ Тренирует мышление команды
❌ Не тестирует реальные системы
2. Simulation Exercise (Симуляция)
Что: Притворяемся что кризис реален, тестируем процедуры
Время: 4-8 часов
Частота: 1 раз в год

Пример:
В субботу 10:00 AM (нерабочее время):
- IT "убивает" primary сервер
- Crisis Team получает alert
- Команда следует BCP шаг-за-шагом
- Восстанавливают из backup
- НО: Клиенты НЕ затронуты (sandbox)

Измеряем:
- Время восстановления: Цель 2ч, Факт 2.5ч ⚠️
- Что сработало: Backup был чистый ✅
- Что не сработало: Процедура устарела ❌
- Улучшения: Автоматизировать failover

Результат:
✅ Тестирует реальные системы
✅ Находит технические проблемы
✅ Команда набирается опыта
❌ Не влияет на клиентов (безопасно, но не 100% реально)
3. Full Exercise (Полная тренировка)
Что: РЕАЛЬНО переключаемся на backup, клиенты затронуты
Время: Полный день
Частота: Опционально (очень рискованно!)

Пример:
В нерабочее время (воскресенье 2 AM):
- Полное переключение на резервную систему
- Клиенты обслуживаются через backup
- Мониторим: есть ли проблемы?
- Через 4 часа: возврат на primary

Риски:
⚠️ Если что-то пойдет не так → реальные проблемы для клиентов
⚠️ Только для очень зрелых организаций

Результат:
✅ 100% реалистично
✅ Максимум уверенности
❌ Очень рискованно
Рекомендация ISO 22301:
Минимум:
- Tabletop: 2 раза в год
- Simulation: 1 раз в год
- Full: Опционально (если готовы)

🔄 Раздел 10: Улучшение
Суть: Становись лучше каждый год
10.1: Корректирующие Действия
После учения/инцидента нашли проблему:

Процесс:
1. Документировать проблему
   "Восстановление заняло 4 часа вместо целевых 2 часов"

2. Анализ причины (Root Cause)
   "Почему?"
   → Процедура устарела
   "Почему процедура устарела?"
   → Никто не обновил после миграции в cloud
   "Почему никто не обновил?"
   → Нет процесса регулярного обзора

3. Корректирующее действие
   "Что сделать?"
   → Обновить процедуру (срок: 2 недели)
   → Внедрить процесс ежеквартального обзора всех BCP
   → Назначить ответственного

4. Проверка эффективности
   Через 3 месяца: Повторное учение
   Результат: 1.5 часа ✅ (Проблема решена!)
10.2: Непрерывное Улучшение
Цикл улучшения:
ГОД 1: Базовый уровень
- BCP планы написаны
- Учения: Восстановление 4 часа
- Проблемы найдены и исправлены

ГОД 2: Автоматизация
- Процедуры автоматизированы (scripts)
- Учения: Восстановление 2 часа ✅
- Новые риски добавлены (пандемия)

ГОД 3: Оптимизация
- Резервная площадка улучшена
- Учения: Восстановление 1 час ✅
- AI внедрен для мониторинга

ГОД 4: Совершенство
- Failover автоматический
- Учения: Восстановление 15 минут ✅
- Организация = resilient champion
Метрики улучшения:
Отслеживаем год-к-году:

1. RTO Achievement
   Год 1: 50% учений достигли RTO
   Год 2: 75% ✅
   Год 3: 95% ✅✅

2. Время восстановления
   Год 1: 4 часа в среднем
   Год 2: 2 часа ✅
   Год 3: 1 час ✅✅

3. Количество проблем
   Год 1: 15 проблем найдено
   Год 2: 8 проблем (улучшение!)
   Год 3: 3 проблемы (отлично!)

4. Готовность персонала
   Год 1: 60% знают свои роли
   Год 2: 85% ✅
   Год 3: 95% ✅✅

→ Штрафы €50K-500K+
→ Потеря лицензии
→ Уголовная ответственность (в крайних случаях)
2. Customer Requirement (Требование клиентов)
B2B клиенты спрашивают:
"У вас есть ISO 22301?"

Если НЕТ:
→ Крупные контракты не подписывают
→ Особенно enterprise клиенты
→ Правительственные тендеры требуют

Если ДА:
→ Конкурентное преимущество
→ Доступ к крупным клиентам
→ Более высокие цены (премиум за надежность)

🎯 ФИЛОСОФИЯ СТАНДАРТА
Главная Идея: RESILIENCE (Устойчивость)
ISO 22301 НЕ про "избежать проблем"
ISO 22301 про "ВЫЖИТЬ несмотря на проблемы"
Метафора: Дерево в Шторм

Слабое дерево (хрупкое):
  Шторм → дерево ломается → дерево мертво

Сильное дерево (resilient):
  Шторм → дерево гнется → шторм прошел → дерево выпрямилось
  Корни стали глубже → дерево СИЛЬНЕЕ чем до шторма

Организация с ISO 22301:
  Кризис → план активирован → организация адаптируется
  Кризис прошел → восстановление завершено
  Lessons learned → планы улучшены
  Организация СИЛЬНЕЕ и ГОТОВЕЕ к следующему кризису
4 Уровня Зрелости:
УРОВЕНЬ 1: FRAGILE (Хрупкий)
  Кризис → Организация умирает
  Пример: Нет плана, нет backup, паника

УРОВЕНЬ 2: ROBUST (Крепкий)
  Кризис → Организация выдерживает (но страдает)
  Пример: Есть backup, но медленное восстановление

УРОВЕНЬ 3: RESILIENT (Устойчивый) ← ISO 22301 ЦЕЛЬ
  Кризис → Быстрое восстановление по плану
  Пример: RTO соблюдено, минимальное воздействие

УРОВЕНЬ 4: ANTIFRAGILE (Анти-хрупкий)
  Кризис → Организация становится СИЛЬНЕЕ
  Пример: Учимся от кризиса, конкуренты умерли - мы выросли
Наша AI платформа цель = ANTIFRAGILE:
AI учится от каждого кризиса всех пользователей
347+ случаев → 100,000+ случаев
Следующий кризис → еще лучше подготовлены
Каждый пользователь делает систему умнее для всех

Специфика НПО:
Отличия от коммерческих организаций:

✅ Миссия > Прибыль
   → Решения принимаются исходя из impact, не ROI

✅ Stakeholders разнообразные:
   - Доноры (платят)
   - Бенефициары (получают помощь)
   - Волонтеры (работают)
   - Общественность (репутация)

✅ Ограниченные ресурсы
   → BCP должны быть LOW-COST
   → Используем волонтеров, бесплатные инструменты

✅ Прозрачность критична
   → Финансовая отчетность публична
   → Любой скандал = потеря доверия = потеря финансирования

Рекомендации для НПО:
1. Emergency Fund = ОБЯЗАТЕЛЕН (6 мес)
2. Диверсификация доноров (никто >30%)
3. Отчетность безупречна (репутация = жизнь)
4. Волонтеры обучены BCM (часть культуры)
5. Cloud-based инструменты (доступны везде)
