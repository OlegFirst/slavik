================================================================================
                          EVENT FLOW DETAILS
================================================================================

EVENT 1: planning.strategy.created
────────────────────────────────────────────────────────────────────────────
Trigger:  POST /api/v1/strategies
Flow:     Client → API → create_strategy() → Database → EventBus → Subscribers
Timing:   Published AFTER successful database insert
Payload:  Strategy metadata (id, number, name, type, phase, status)
Subscribers:
  • BIA Service       → Link strategy to BIA results
  • Risk Service      → Update related risks
  • Audit Service     → Log strategy creation
  • Notification      → Notify stakeholders

EVENT 2: planning.strategy.approved
────────────────────────────────────────────────────────────────────────────
Trigger:  POST /api/v1/strategies/{id}/approve
Flow:     Client → API → approve_strategy() → Database → EventBus → Subscribers
Timing:   Published AFTER successful status update to APPROVED
Payload:  Strategy metadata + approval info (approved_by, notes, timestamp)
Subscribers:
  • BIA Service           → Activate related processes
  • Implementation        → Start planning implementation
  • Governance            → Update compliance status
  • Notification          → Notify implementation team

EVENT 3: planning.cost_benefit.completed
────────────────────────────────────────────────────────────────────────────
Trigger:  POST /api/v1/strategies/{id}/cost-benefit
Flow:     Client → API → calculate_cost_benefit() → Database → EventBus → Subs
Timing:   Published AFTER successful calculation and database update
Payload:  Financial analysis (costs, benefits, ROI, NPV, recommendation)
Subscribers:
  • Finance Service   → Record budget data
  • Reporting         → Update financial reports
  • Dashboard         → Update ROI metrics
  • Analytics         → Store for analysis

================================================================================
                          ERROR HANDLING FLOW
================================================================================

┌─────────────────────────────────────────────────────────────────────────┐
│  Business Operation (e.g., create_strategy)                             │
│  ├─ Validate input                                                      │
│  ├─ Execute database operation                                          │
│  ├─ ✅ Success? Continue...                                            │
│  │                                                                      │
│  └─ Try: Publish Event                                                  │
│     ├─ async with httpx.AsyncClient() as client:                       │
│     │   └─ await client.post(..., timeout=5.0)                         │
│     │                                                                   │
│     ├─ ✅ Success Case:                                                │
│     │   ├─ Event published to EventBus                                 │
│     │   ├─ logger.info("Published event...")                           │
│     │   └─ Continue to return response                                 │
│     │                                                                   │
│     └─ ❌ Failure Case (EventBus down, timeout, network error):       │
│         ├─ Exception caught                                            │
│         ├─ logger.warning("Failed to publish...")                      │
│         ├─ NO re-raise (graceful degradation)                          │
│         └─ Continue to return response                                 │
│                                                                         │
│  └─ Return successful response (regardless of event publish status)    │
└─────────────────────────────────────────────────────────────────────────┘

Key Points:
  ✅ Database operation MUST succeed first
  ✅ Event publishing is ASYNCHRONOUS
  ✅ Event failures are LOGGED but NOT blocking
  ✅ User receives success response even if event fails
  ✅ EventBus unavailability does NOT break business logic

Client          API             Service         Database        EventBus      Subs
  |              |                |                |               |            |

  |   /strategies|                |                |               |            |
  |              |--create------->|                |               |            |

  |              |                |   Strategy     |               |            |
  |              |                |<--Success------|               |            |
  |              |                |                |               |            |
  |              |                |--try: publish_event()--------->|            |
  |              |                |  topic: planning.strategy.created          |
  |              |                |                |               |            |
  |              |                |                |        [EventBus stores]   |
  |              |                |                |               |            |
  |              |                |                |               |--notify--->|
  |              |                |                |               | all subs   |
  |              |                |<--Success (or graceful fail)---|            |
  |              |                |                |               |            |
  |              |<--Response-----|                |               |            |
  |<--200 OK-----|                |                |               |            |
  | (Strategy)   |                |                |               |            |
  |              |                |                |               |            |

Timeline:
  T+0ms:    Client sends POST request
  T+50ms:   Service validates input
  T+100ms:  Database INSERT completes
  T+110ms:  Event publishing starts (async)
  T+130ms:  EventBus receives event (or timeout at T+5000ms)
  T+135ms:  Response returned to client (regardless of event status)
  T+150ms:  Subscribers receive event (asynchronously)

EVENTBUS_URL=http://localhost:8001     # EventBus service URL
SERVICE_NAME=planning_service            # Service identifier
DATABASE_URL=postgresql+asyncpg://...   # Database connection
LOG_LEVEL=INFO                          # Logging level

Docker Compose:
────────────────────────────────────────────────────────────────────────────
services:
  planning_service:
    image: bcm/planning-service:latest
    ports:
      - "8011:8011"
    environment:
      - EVENTBUS_URL=http://eventbus:8001
      - DATABASE_URL=postgresql+asyncpg://bcm:bcm@db:5432/bcm
    depends_on:
      - eventbus
      - database

  eventbus:
    image: bcm/eventbus:latest
    ports:
      - "8001:8001"
