EventBus Choreography

The Nervous System: Connecting All Services

Event-Driven • Choreography Pattern • Redis Streams • At-Least-Once Delivery

The Communication Backbone of the Platform

EventBus is the "Nervous System" enabling services to communicate without knowing about each other. Like nerves transmitting signals throughout the body, EventBus carries events across the platform.

Think of it as the "Post Office" - services publish events (send letters), EventBus delivers them to subscribers (recipients), and everyone stays loosely coupled.

Orchestration vs Choreography: Two Design Patterns

Understanding why we chose Choreography for microservices communication

Orchestration Pattern

Central Conductor - One service controls the workflow

graph TD
    Orchestrator[Central Orchestrator] --> S1[Service 1]
    Orchestrator --> S2[Service 2]
    Orchestrator --> S3[Service 3]
    Orchestrator --> S4[Service 4]

    S1 --> Orchestrator
    S2 --> Orchestrator
    S3 --> Orchestrator
    S4 --> Orchestrator

    style Orchestrator fill:#f5576c,color:#fff

Characteristics:

  • ✓ Central control and visibility
  • ✓ Easy to understand flow
  • ✓ Good for complex workflows
  • ✗ Single point of failure
  • ✗ Tight coupling to orchestrator
  • ✗ Hard to scale independently

Example: Workflow Intelligence orchestrates BIA workflow (PLAN → DO → CHECK → ACT)

Choreography Pattern

Distributed Dance - Services react to events independently

graph LR
    S1[Service 1] -.event.-> EventBus((EventBus))
    EventBus -.->|subscribe| S2[Service 2]
    EventBus -.->|subscribe| S3[Service 3]
    S2 -.event.-> EventBus
    EventBus -.->|subscribe| S4[Service 4]

    style EventBus fill:#4facfe,color:#fff

Characteristics:

  • ✓ Loose coupling (services independent)
  • ✓ No single point of failure
  • ✓ Easy to add new services
  • ✓ Scales naturally
  • ✗ Harder to visualize flow
  • ✗ Need distributed tracing

Example: BIA service publishes `process.created` → Analytics, Workflow Intelligence, and Monitoring all react independently

Our Approach: Hybrid Pattern

We use BOTH patterns where each fits best:

Orchestration For:

  • Complex PDCA workflows (Workflow Intelligence)
  • Multi-step BIA/Risk processes
  • Validation pipelines

Choreography For:

  • Cross-service notifications
  • Analytics & monitoring
  • Cache invalidation
  • Audit logging

Layer 1: Services

All 62 platform services interact with EventBus through a simple interface.

  • Publishers: Create events, call `publish()`
  • Subscribers: Register handlers with `subscribe()`
  • No backend knowledge: Code works with any backend

Layer 2: Core Interface

Abstract contract (IEventBus) that all backends must implement.

  • Type-safe: Event class with validation
  • Pattern matching: `workflow.*`, `bia.*`
  • Metadata: timestamp, source, tenant, correlation_id

Layer 3: Backends

Pluggable implementations for different deployment scenarios.

  • Memory: MVP, testing, single-process
  • Redis Streams: Production, multi-instance
  • RabbitMQ: Future, high-volume

Key Concepts Illustrated

1. Publish (Fire and Forget)

BIA Service publishes event and continues immediately. It doesn't wait for subscribers or care who receives it. 

event = Event.create(
    event_type='bia.process_created',
    data={'process_id': 123},
    source='bia-service',
    tenant_id='tenant_123'
)
await bus.publish(event)  # Returns immediately

2. Subscribe (Pattern Matching)

Services subscribe to event patterns. Multiple services can subscribe to the same event. 

async def handle_bia_event(event: Event):
    process_id = event.data['process_id']
    await update_workflow(process_id)

await bus.subscribe('bia.*', handle_bia_event)

3. Consumer Groups (Load Balancing)

Multiple instances of same service = consumer group. Each event delivered to ONE instance. 

# Instance 1
await bus.subscribe(
    'bia.*',
    handler,
    consumer_group='workflow-processors'
)

# Instance 2 (same group)
# Event goes to instance 1 OR 2, not both

4. At-Least-Once Delivery

Events delivered at least once (may have duplicates). Handlers should be idempotent. 

async def idempotent_handler(event: Event):
    # Check if already processed
    if await db.exists('processed', event.id):
        return  # Skip duplicate

    # Process event
    await process(event)

    # Mark as processed
    await db.save('processed', event.id)

# All BIA events

# All events from BIA and Risk
await bus.subscribe(['bia.*', 'risk.*'], handler)

# Everything (use carefully!)
await bus.subscribe('*', handler)

Backend Comparison: Memory vs Redis Streams

Choose the right backend for your deployment scenario

Feature InMemory Backend Redis Streams Backend RabbitMQ (Future)
Use Case MVP, Testing, Development Production, Multi-instance High-volume, Complex routing
Persistence ✗ Lost on restart ✓ Durable (Redis RDB/AOF) ✓ Durable (disk/memory)
Multi-instance ✗ Single process only ✓ Consumer groups ✓ Multiple consumers
Event History ✗ No replay ✓ Replay from timestamp ⚠️ Limited retention
Publish Latency <1ms (in-memory) <5ms (network + Redis) <3ms (network + MQ)
Throughput 10K+ events/sec 1K+ events/sec 10K+ events/sec
Pattern Matching ✓ Regex-based ⚠️ Multiple streams ✓ Topic + routing keys
Setup Complexity Zero dependencies Requires Redis Requires RabbitMQ
Delivery Guarantee At-least-once (best effort) At-least-once (ACK) At-least-once / Exactly-once
Code Changes ✓ ZERO - Just change config!

What Happened:

  1. User Interface sends HTTP POST to BIA Service
  2. BIA Service creates process in database, publishes event, returns immediately
  3. EventBus stores event in Redis Stream, starts delivering to subscribers
  4. 4 Subscribers react independently:
    • Workflow Intelligence creates implementation roadmap
    • Analytics increments metrics counter
    • Monitoring logs event for audit trail
    • Notification sends email to admin
  5. Result: Loose coupling - BIA Service doesn't know about subscribers, easy to add new reactions

Key Benefits of Event-Driven Architecture

1. Loose Coupling

Services don't know about each other, only about events.

  • Add new services without modifying existing ones
  • Change service internals independently
  • Remove services without breaking others

Result: Easier maintenance, faster feature development

2. Scalability

Scale services independently based on load.

  • Consumer groups distribute load across instances
  • High-traffic services scale horizontally
  • No single bottleneck

Result: Handle 10x growth without architectural changes

3. Resilience

System continues working even if some services fail.

  • Events persisted in Redis (survive restarts)
  • Failed handlers retry automatically
  • No cascading failures

Result: 99.9% uptime even with partial outages

4. Observability

See everything happening across the platform.

  • Every interaction creates an event
  • Correlation IDs link related events
  • Full audit trail automatically

Result: Debug issues 5x faster with event history

5. Extensibility

Add new functionality without touching core services.

  • New analytics? Just subscribe to events
  • New notification channel? Subscribe and send
  • A/B testing? Subscribe with filters

Result: Ship features 3x faster

6. Time Travel

Replay events to rebuild state or fix issues.

  • Redis Streams keep event history
  • Replay from any timestamp
  • Rebuild analytics after bug fix

Result: Recover from data corruption in minutes
